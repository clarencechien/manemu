# ADR(Architecture Decision Records)

重大取捨的決策記錄。一條 ADR = 一個決策:背景 → 決策 → 理由 → 後果。
新決策往下加;推翻舊決策時不改舊條目,寫新條目並註明取代關係。

## ADR-001 音檔留存:譯音存使用者裝置,伺服器零留存(2026-08-06)

**狀態**:採納(取代 v16 短暫的「一律純文字」設定)

**背景**:本地翻譯紀錄(IndexedDB)上線時,譯音是否留存反覆了兩版——
v15 存譯音 WAV、v16 收斂成純文字(僅測試模式附音檔)。需要定案。

**決策**:

| 資料 | 使用者裝置(IndexedDB) | 伺服器 |
| --- | --- | --- |
| 輸入音檔(使用者原聲) | **永不存** | **永不存** |
| 譯音(引擎輸出) | **存**(WAV Blob,隨紀錄) | 永不存 |
| 對話文字 | 存 | 永不存 |
| 🧪 測試模式 | — | 唯一例外:明示同意後錄音+文字上傳 R2 |

**理由**:

1. **譯音重放是核心功能,不是 nice-to-have**——旅途實況:對方沒聽清、吵雜環境、
   隔天要再用同一句(「昨天那句退稅怎麼說」)。重放只能靠本地留檔。
2. **譯音的隱私敏感度低於原聲**:它是機器合成的聲音,不含使用者聲紋;
   語意內容與文字紀錄等價,存文字不存譯音在隱私上不構成實質差異。
3. **原聲是聲紋級敏感資料**,且重放它沒有產品價值 → 任何端都不存,永久原則。
4. 「伺服器零留存」是對外承諾與賣點,**本地留存不牴觸它**——紀錄與音檔在使用者
   手上,刪除權也在使用者手上(逐組刪/清空/瀏覽器清資料)。

**後果**:

- IndexedDB 容量:400 句修剪上限,譯音 WAV 粗估 <100MB,行動裝置可承受。
- 私密瀏覽/舊瀏覽器存不了 Blob → 自動降級純文字;IDB 全失敗 → 靜默停用,不影響翻譯。
- 面板文案需講清楚三層:「紀錄與譯音只存在此裝置、不上傳;你的原聲不會被任何一端保存」。

## ADR-002 對話模型:按住說話(PTT),不做連續開麥(2026-08-06)

**狀態**:採納

**背景**:PTT(walkie-talkie 式)原本是為了「死氣可控」而選的。反過來問:
如果拿掉按鈕、讓兩個不同語言的人連續交談,成功率與品質會不會一樣好?

**決策**:維持 PTT。連續開麥(open mic)不做,除非先解掉下面三個機制問題。
中間態「免持單句」(點一下開始、VAD 判定結束)列為未來可選,風險遠低於全連續。

**理由**:退化的不是「翻譯」,是「聽」與「可靠性」——正好打在已知弱點上
(findings:24 筆共識災難有 23 筆來自 STT 階段)。翻譯內核不變,但輸入會變髒:

1. **回音自噬(最嚴重,是失控不是降級)**:PTT 是半雙工,播譯音時麥克風關閉。
   open mic 下裝置播出的日語會被自己的麥克風收回 → STT 聽到日語 → 引擎當成新輸入
   翻成中文 → 再播 → 迴圈。瀏覽器 `echoCancellation` 是為 WebRTC 通話設計,
   外放 + 吵雜環境殘留大。這一項單獨就足以讓連續模式在餐廳崩掉。
2. **翻譯方向要用猜的**:按鈕本身是最強信號(按這顆=中→日,按那顆=日→中)。
   open mic 得靠語言辨識判方向,而旅遊場景最常混語(「這個 sumimasen 多少錢」);
   判錯 = 把日語當中文翻 = 直接災難。架構代價:relay 每個 session 綁一個方向 +
   一份 systemInstruction,雙向連續 = 兩條 session(成本 ×2)或動態切換(延遲+狀態複雜)。
3. **切分點會切壞句子**(有第一手證據):live-translate 連續 session 的 `turnComplete`
   **從不觸發**,現行是自己用 RMS + 2.5s 靜音收斂。車站/市集的持續噪音會讓 RMS 一直
   判成「有聲」→ 要嘛不收斂、要嘛切在句中。「這個不要辣」切成「這個不要」+「辣」,
   譯文就毀了(T014 辣→啦 已示範這類邊界錯誤的殺傷力)。

**預期數字**:單句 adequacy 不會從 4.85 掉到 3.x;但**災難率**會從 0.7–2% 上升——
估計安靜環境(旅館櫃檯、近距離)3–5%,目標場景(餐廳、車站、市集)10% 以上。
使用者體感不是「翻得差」而是「常出現莫名其妙的句子」,更難原諒。

**反直覺的一點:open mic 的死氣會變長。** PTT 的「放開手」是零成本零誤差的句子結束
信號,引擎立刻能翻;open mic 得等 VAD 判定靜音(現行 2.5s),死氣反而增加。
要連續又要低死氣,只能用邊講邊翻的搶跑(translate 專用模式)——而那個模式實測
災難率 8%、問句保留 91%,正是當初不選它的原因。**三選二:連續對話、低死氣、高品質。**

**後果**:

- 計價模型與 PTT 綁定:現在賣 session 牆鐘時間、每句 10–20 秒。open mic 下 session
  得一直開著(靜默也在傳),30 分鐘對話 = 30 分鐘串流計費,`SESSION_HARD_CAP_S=120`
  這道保險絲也失效——pricing.md「牆鐘計量 vs 音訊秒計費」那層安全邊際會反轉成負的。
- 未來要做 open mic,三條路(難度遞增):**雙裝置/耳機**(每人一台各收各的,物理隔離
  同時解回音+方向+切分,Timekettle 那類產品的解法;我們的架構開兩條 session 不難,
  難在配對與同步)→ **免持單句**(保留方向明確與半雙工,只拿掉「按著」的不便,
  災難率應幾乎不變)→ **全連續**(得先強制耳機/近距離收音解回音、再讓使用者選
  「現在誰在講」解方向;解完之後跟 PTT 的差別也只剩手不用按著)。
